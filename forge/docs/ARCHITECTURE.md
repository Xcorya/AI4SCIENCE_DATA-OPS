# FORGE 设计说明

FORGE 将采购决策拆成固定规格、可解释比较、状态变更和签名交付四层。运行时不依赖外部服务。

## 模块

| 文件 | 职责 |
|---|---|
| `forge/protocol.py` | JSON 规范化、SHA-256、HMAC、字段与交付校验 |
| `forge/engine.py` | 报价字段校验、硬筛选、预计可用成本、Pareto |
| `forge/store.py` | SQLite 事务、需求/报价/订单/交付/报告/事件 |
| `forge/httpd.py` | 本地 HTTP、JSON API、静态文件、Host/Origin 检查 |
| `forge/__main__.py` | 启动参数、密钥配置、演示播种 |
| `web/app.js` | 页面渲染、操作提交、JSON 文件导入导出 |

存储层对多步写入使用 `BEGIN IMMEDIATE`，避免并发草案绕过单需求单订单限制。约束失败回滚事务，不留下半个交付或半个采购单。SQLite 每次操作使用独立连接。

## 实体

| 实体 | 不变内容与关系 |
|---|---|
| demand | 固定 spec 与 spec_hash |
| quote | 属于 demand，报价及许可声明不可原地修改 |
| order | 固定 spec 和 quote 快照，状态及当前交付/报告引用可更新 |
| delivery | 属于 order，固定批次 ID、完整正文与签名 |
| report | 固定收到的 AEGIS 签名正文 |
| event | 时间、动作、对象 ID、详情，按序号追踪 |

报价修改、规格修订通过新需求/新报价表达。此版不实现合同版本管理。

## 状态机

```text
draft ──release──▶ ordered ──deliver──▶ delivered
                                        │
                         apply_report ──┼──▶ accepted（终态）
                                        ├──▶ review ───┐
                                        └──▶ rejected ─┤
                                                      │
                                    新交付 ID ◀────────┘
                                          │
                                          └──▶ delivered
```

只有 `ordered/review/rejected` 可登记交付。`delivered` 需要先取得当前交付决定。一个当前交付只能应用一份决定；完全相同的报告重放是幂等操作。

报告导入先验证签名、协议和有效期，再在事务内读取当前订单/交付核对身份、规格哈希、数据哈希、原交付正文哈希。旧报告即使签名有效，也不能覆盖当前新交付。

## 采购算法

总价 = 数量 × 整数单价 + 整数固定费。候选必须满足：同币种、够容量、不超单批预算、交期足够、权限已记录核验、目的包含、地区包含，以及需要时允许派生。

合格集合用 Fraction 精确比较 `总成本 / (数量 × 声明质量)`，不使用已四舍五入的显示值排序。质量为零不除零，结果为空并放在同组末尾；极小正质量超出浮点显示范围时输出 null，但精确排序仍有效。无合格报价时不创建订单。

Pareto 使用三维支配关系（成本 ↓、交期 ↓、声明质量 ↑），不是单一“最佳供应商”保证。当前实现是 O(Q²)，适合本地小规模询价。

## 本地边界

HTTP 服务只监听 IPv4 loopback，检查 Host，限制变更请求 Origin 和 `application/json`，提供静态资源目录边界、CSP、完整请求帧校验与 5 秒读取停顿超时。GET/POST 都返回结构化内部错误，数据库上下文完成后显式关闭连接。

这些检查不能阻止恶意本机用户、被控制的浏览器或持有数据库/密钥的人。没有身份认证、正式审批、外部调用或财务交易。

## 可扩展方向

大规模采购应把报价有效期、证据附件、审批身份、预算占用和供应商分单建模成独立实体。生产签名需分离角色；不能把当前公共演示或共享密钥方案直接用于不可信交易参与者。
